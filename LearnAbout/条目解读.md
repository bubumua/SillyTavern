## 一、角色卡整体结构

SillyTavern 官方文档说明，SillyTavern 以“character cards”为核心；角色卡是一组提示词/定义，用来设定 LLM 的行为并支持持久聊天。角色卡内容可以是角色、抽象场景、任务助手、名人或虚构人物。

### 1. V2 角色卡顶层结构

典型 V2 角色卡：

```json
{
  "spec": "chara_card_v2",
  "spec_version": "2.0",
  "data": {
    "name": "...",
    "description": "...",
    "personality": "...",
    "scenario": "...",
    "first_mes": "...",
    "mes_example": "...",
    "creator_notes": "...",
    "system_prompt": "...",
    "post_history_instructions": "...",
    "alternate_greetings": [],
    "tags": [],
    "creator": "...",
    "character_version": "...",
    "extensions": {},
    "character_book": {
      "entries": []
    }
  }
}
```

SillyTavern 也常在顶层保留 V1/兼容镜像字段，例如 `name`、`description`、`first_mes`、`creatorcomment`、`talkativeness`、`fav`、`tags`。本项目序列化时会同时更新顶层兼容字段和 `data` 内字段，以减少导入导出兼容问题。

### 2. 顶层 key 解读

| key | 类型 | 含义 | 编辑建议 |
| --- | --- | --- | --- |
| `spec` | string | 角色卡规范标识。V2 通常是 `chara_card_v2`，V3 可能是 `chara_card_v3`。 | 不要随意改。它决定解析器如何识别卡片格式。 |
| `spec_version` | string/number | 规范版本。V2 通常是 `2.0`。 | 不要用 UI 编辑；格式迁移应由专门逻辑处理。 |
| `data` | object | V2/V3 主数据容器，角色定义主要都在这里。 | 角色编辑器应主要读写这里。 |
| `name` | string | V1 兼容镜像：角色名。 | 应与 `data.name` 保持一致。 |
| `description` | string | V1 兼容镜像：角色描述。 | 应与 `data.description` 保持一致。 |
| `personality` | string | V1 兼容镜像：性格摘要。 | 应与 `data.personality` 保持一致。 |
| `scenario` | string | V1 兼容镜像：对话场景。 | 应与 `data.scenario` 保持一致。 |
| `first_mes` | string | V1 兼容镜像：首条消息/开场白。 | 应与 `data.first_mes` 保持一致。 |
| `mes_example` | string | V1 兼容镜像：示例对话。 | 应与 `data.mes_example` 保持一致。 |
| `creatorcomment` | string | V1/旧版兼容：创作者备注。 | 通常对应 `data.creator_notes`。 |
| `tags` | string[] | V1/兼容：标签。 | 通常对应 `data.tags`。 |
| `talkativeness` | number/string | 旧版/兼容：群聊自然发言概率。 | 通常对应 `data.extensions.talkativeness`。 |
| `fav` | boolean/string | 旧版/兼容：收藏状态。 | 通常对应 `data.extensions.fav`。 |
| `avatar` | string | SillyTavern 服务端内部字段，通常是头像文件名/唯一标识。 | 不建议在编辑器中改。 |
| `chat` | string | 当前聊天文件名，常见于 SillyTavern 内部对象。 | 不属于卡片语义定义，导出时应谨慎保留。 |
| `create_date` | string | 创建时间或导出时间。 | 元数据，可保留。 |
| `json_data` | string | SillyTavern 内部可能保存的原始 JSON。 | 不建议手动改。 |
| `shallow` | boolean | SillyTavern 懒加载/浅对象标记。 | 内部状态，不应写入用户导出的卡片。 |

## 二、角色卡 `data` 下每个 key

官方 Character Design 文档把角色定义分成永久定义、首条消息、示例消息、高级定义、作者元数据、角色注入等部分。官方文档明确说明：角色名、描述、性格、场景属于每次生成都会发送的“永久 tokens”；首条消息只在开局进入上下文；示例消息会在上下文空间不足时被逐块挤出，除非设置强制保留。

### 1. 基础角色定义

| key | 类型 | UI/概念 | 含义 | 进入提示词的方式 |
| --- | --- | --- | --- | --- |
| `name` | string | Character Name | 角色名。SillyTavern 用它替换 `{{char}}` 宏，也用它标识角色。 | 永久信息；通常每次生成都会参与上下文。 |
| `description` | string | Description | 角色描述，可写身份、外貌、背景、行为规则、世界观摘要等。 | 永久信息；Context Template 可用 `{{description}}` 引用。 |
| `personality` | string | Personality summary | 官方文档称为性格简述。更适合稳定人格、语气、价值观、习惯。 | 永久信息；Context Template 可用 `{{personality}}` 引用。 |
| `scenario` | string | Scenario | 当前对话发生的背景、处境、关系、初始舞台。 | 永久信息；Context Template 可用 `{{scenario}}` 引用。 |
| `first_mes` | string | First Message | 角色开场白。官方文档强调它会显著影响后续回复的风格、长度和表达方式。支持 Markdown/HTML。 | 通常只作为新聊天开头消息进入一次，不是每轮永久定义。 |
| `mes_example` | string | Examples of dialogue | 示例对话，用 `<START>` 分隔多个示例块。用于展示角色说话方式。 | 有空间时进入上下文；上下文满时可逐块被挤出。 |

编辑建议：

- `description` 不宜堆所有信息。长期稳定、每轮都必须知道的信息可以放这里；大量世界细节更适合 `character_book`。
- `scenario` 是当前局面，不一定适合写完整世界设定。复杂设定更适合 lorebook/World Info。
- `first_mes` 是非常强的风格示范。想让角色短句、长段、第三人称、动作描写明显，开场白比单纯说明更有效。
- `mes_example` 要用 `{{user}}:` 和 `{{char}}:` 前缀；`<START>` 是块分隔标记，不会原样进入最终提示词，而会被模板中的示例分隔符替换。

### 2. 高级定义与作者元数据

| key | 类型 | UI/概念 | 含义 | 使用条件 |
| --- | --- | --- | --- | --- |
| `creator_notes` | string | Creator's Notes | 创作者说明、使用说明、版本说明。官方文档说明它不用于 prompt building，主要是元数据展示。 | 默认不作为提示词内容，除非被宏或插件引用。 |
| `system_prompt` | string | Main Prompt override / Prompt Overrides | 角色级主提示词覆盖。若用户设置启用“Prefer Char. Prompt”，这里会覆盖默认主/系统提示词。可用 `{{original}}` 插入原默认提示。 | 依赖 SillyTavern 用户设置。 |
| `post_history_instructions` | string | Post-History Instructions override | 角色级后历史指令。若用户设置启用“Prefer Char. Instructions”，这里会作为该角色的 PHI。可用 `{{original}}` 保留全局 PHI。 | 依赖 SillyTavern 用户设置。 |
| `tags` | string[] | Tags to Embed | 标签。官方文档说“Tags to Embed”可嵌入角色描述；导入时不一定自动合并到本地标签库。 | 元数据/搜索/可选嵌入。 |
| `creator` | string | Created by | 创作者名。可用于角色列表副标题。 | 元数据，不直接影响模型。 |
| `character_version` | string | Character Version | 角色版本号。可用于列表显示，也有 `{{charVersion}}` 宏。 | 元数据，可被宏引用。 |

### 3. 问候语与群聊相关

| key | 类型 | 含义 | 官方行为 |
| --- | --- | --- | --- |
| `alternate_greetings` | string[] | 备用开场白。 | 官方文档说明：它们会作为新聊天第一条消息的额外 swipe；如果角色在群聊中，系统会随机选择一个问候语开始。 |
| `group_only_greetings` | unknown | 群聊专用问候语扩展字段。 | 官方文档未作为核心 key 详细说明；本项目只保留原值，不做强语义解释。 |

### 4. `extensions`

`extensions` 是 V2 规范为应用和插件保留的扩展对象。官方扩展开发文档也说明可以向角色卡 JSON 写入扩展数据。编辑器必须保留未知 key。

| key | 类型 | 含义 | 备注 |
| --- | --- | --- | --- |
| `talkativeness` | number | 群聊自然激活顺序下角色被触发发言的概率。官方 Character Design 文档说明范围是 0% 到 100%，默认 50%。 | SillyTavern 源码默认值约为 `0.5`。 |
| `fav` | boolean | 收藏状态。 | UI 元数据。 |
| `world` | string | 关联世界/世界书名称或插件使用字段。 | 不是官方 Character Design 文档核心字段；应保留。 |
| `depth_prompt` | object | 角色注入/Character's Note。 | 见下表。 |
| `regex_scripts` | object[] | 角色 scoped Regex 脚本。 | Regex 扩展会把“Scoped”脚本保存到角色卡扩展数据中。 |
| 其他 key | unknown | 插件或第三方工具自定义数据，例如 `tavern_helper`、站点来源、图像提示词等。 | 不应删除；编辑器应原样保留。 |

`depth_prompt`：

| key | 类型 | 含义 |
| --- | --- | --- |
| `prompt` | string | 注入文本。官方 Character Design 文档称 Character's Note：用于在固定深度插入角色补强提示，常用于强化角色特征。 |
| `depth` | number | 插入深度。从最新消息向上数；`0` 表示最后一条消息之后。 |
| `role` | `"system"` / `"user"` / `"assistant"` | 作为哪种角色消息插入。官方文档列出 User、System、Assistant。 |

## 三、角色卡 `character_book`

`data.character_book` 是嵌入角色卡里的 lorebook / World Info。官方 World Info 文档说明：World Info 像动态字典，按关键词激活条目并把条目内容插入 prompt；它能补充世界、记忆、规则、随机事件等，但不保证模型一定遵守。

### 1. `character_book` 顶层 key

| key | 类型 | 含义 |
| --- | --- | --- |
| `name` | string | 角色书名称。没有时 SillyTavern 可能用角色名生成默认名称。 |
| `description` | string | 角色书描述。V2 类型支持，但本项目当前不编辑。 |
| `scan_depth` | number | 该书扫描聊天历史的深度。World Info 官方文档说明 scan depth 表示扫描最近多少条消息；`1` 表示只扫最后一条，`2` 表示最后两条。 |
| `token_budget` | number | 条目最多占用的 token 预算。官方文档说明预算耗尽后即使 key 命中也不会继续插入更多条目。 |
| `recursive_scanning` | boolean | 是否允许条目内容继续触发其他条目。 |
| `extensions` | object | 书级扩展对象。必须保留未知字段。 |
| `entries` | object[] | World Info 条目列表。 |

### 2. `entries[]` 每个条目 key

| key | 类型 | 含义 | 编辑注意 |
| --- | --- | --- | --- |
| `id` | number/string | 条目唯一 ID。 | SillyTavern 用它定位条目；不要随意重复。 |
| `keys` | string[] | 主关键词。官方文档说明它们触发条目激活，默认不区分大小写；也支持 JavaScript regex 风格的 `/pattern/flags`。 | 关键词太泛会频繁触发。 |
| `secondary_keys` | string[] | 次级关键词/过滤关键词。 | 和 `selective`、`selectiveLogic` 共同决定是否激活。 |
| `comment` | string | 条目标题/备注。官方 World Info 文档称 Entry Title / Memo，不参与 AI 或触发逻辑。 | 适合写人类可读标签。 |
| `name` | string | 部分 V2/工具使用的条目名。 | 与 `comment` 类似，兼容字段。 |
| `content` | string | 条目被激活后插入 prompt 的正文。官方文档明确这是实际插入文本。 | 真正影响模型的核心字段。 |
| `constant` | boolean | 常驻条目。官方 World Info “蓝色圆点”语义：总是尝试进入 prompt。 | 仍受预算等限制。 |
| `selective` | boolean | 是否启用双 key / 条件触发。 | 通常与 `secondary_keys` 配合。 |
| `insertion_order` | number | 插入顺序/优先级。官方文档说明多个条目同时激活时，数值越大越靠近上下文末尾，通常影响更强。 | 常见默认值 `100`。 |
| `enabled` | boolean | 条目是否启用。官方文档说明每个条目有启用/禁用开关。 | `false` 时不应参与触发。 |
| `position` | string | V2 简化插入位置，常见为 `before_char` / `after_char`。 | 对应“角色定义前/后”附近；SillyTavern 扩展里还可用更细的 `extensions.position`。 |
| `use_regex` | boolean | 是否把 key 当正则/正则模式使用的兼容开关。 | 新版 ST 也能从 `/.../flags` 形式识别正则。 |
| `case_sensitive` | boolean | key 是否区分大小写。 | 也可能出现在 `extensions.case_sensitive`。 |
| `priority` | number | 优先级/预算相关字段。 | 不是本项目当前核心 UI 字段；保留。 |
| `extensions` | object | 条目扩展设置。 | SillyTavern World Info 许多高级设置都存这里。 |

### 3. `entries[].extensions` 常见 key

SillyTavern 源码把很多 World Info UI 设置映射到 `extensions`。以下是常见 key：

| key | 类型 | 含义 |
| --- | --- | --- |
| `display_index` | number | UI 展示顺序。拖拽排序常更新它。 |
| `position` | number | 更细的插入位置。不同数字映射 World Info UI 的位置，例如角色定义前/后、示例消息前/后、Author's Note 顶/底、指定深度、Outlet 等。 |
| `role` | number | 当位置是 in-chat / depth 时使用的消息角色。 |
| `depth` | number/null | 指定深度插入时的深度。官方文档说明 `0` 是 prompt 底部/最后消息之后。 |
| `probability` | number | 触发概率。官方文档说明 `100` 每次激活都插入，`50` 约一半概率，`0` 等于不插入。 |
| `useProbability` | boolean | 是否启用概率检查。 |
| `selectiveLogic` | number | 次级 key 逻辑。官方文档列出 AND ANY、AND ALL、NOT ANY、NOT ALL 四种语义。 |
| `group` | string | Inclusion Group 标签。官方文档说明同组多个条目同时触发时通常只插入一个。 |
| `group_override` | boolean | 覆盖/优先使用组逻辑的开关。 |
| `group_weight` | number | 组内随机权重。官方文档说明权重越高，被选中概率越高。 |
| `use_group_scoring` | boolean/null | 是否按 key 命中数对组内候选评分。官方文档说明可让更具体条目胜出。 |
| `scan_depth` | number/null | 条目级扫描深度覆盖。 |
| `match_whole_words` | boolean/null | 是否只匹配完整词。官方文档提醒中文/日文等无空格语言可能不适合开启。 |
| `case_sensitive` | boolean/null | 条目级大小写敏感覆盖。 |
| `automation_id` | string | 自动化 ID。官方文档说明可与 Quick Replies / STscript 的同 ID 命令联动。 |
| `vectorized` | boolean | 是否标记为向量化条目。官方文档说明向量化只是额外激活方式，普通 key 仍可触发。 |
| `exclude_recursion` | boolean | 排除递归触发。 |
| `prevent_recursion` | boolean | 防止该条目参与递归。 |
| `delay_until_recursion` | boolean | 仅在递归阶段检查。 |
| `sticky` | number/null | Sticky timed effect。官方文档说明条目激活后保持 N 条消息。 |
| `cooldown` | number/null | Cooldown timed effect。激活后 N 条消息内不能再次激活。 |
| `delay` | number/null | Delay timed effect。聊天消息数达到 N 前不可激活。 |
| `triggers` | string[] | 生成类型过滤。可限制普通生成、继续、重生成、后台 quiet 等类型。 |
| `ignore_budget` | boolean | 是否忽略预算的扩展开关。应谨慎使用。 |
| `outlet_name` | string | Outlet 插入位置的名称。官方文档说明可用 `{{outlet::Name}}` 在 Prompt Manager 或高级格式化中手动取出同名条目内容。 |
| `match_persona_description` | boolean | 是否把 persona 描述作为匹配来源。 |
| `match_character_description` | boolean | 是否把角色 description 作为匹配来源。 |
| `match_character_personality` | boolean | 是否把角色 personality 作为匹配来源。 |
| `match_character_depth_prompt` | boolean | 是否把角色 depth prompt / Character's Note 作为匹配来源。 |
| `match_scenario` | boolean | 是否把 scenario 作为匹配来源。 |
| `match_creator_notes` | boolean | 是否把 creator notes 作为匹配来源。 |

## 四、角色卡 `regex_scripts`

路径：`data.extensions.regex_scripts[]`

官方 Regex 文档说明：Regex 扩展会自动检测文本模式并做替换，可用于聊天内容、发往模型的 prompt、slash 命令、World Info 等。Regex 脚本有 Global、Scoped、Preset 三种存储位置；角色卡里的 `regex_scripts` 属于 Scoped 脚本。

| key | 类型 | 含义 |
| --- | --- | --- |
| `id` | string | 脚本 UUID。 |
| `scriptName` | string | 脚本名称。官方文档说明它是脚本列表中的标签，也可被命令触发时引用。 |
| `disabled` | boolean | 是否禁用。禁用脚本不会触发。 |
| `runOnEdit` | boolean | 是否在消息被编辑后也运行。官方文档称 “Run on Edit”。 |
| `findRegex` | string | 查找正则。官方文档说明它是检测目标文本模式的核心字段，支持 `/pattern/flags`。 |
| `replaceString` | string | 替换文本。可使用 `{{match}}` 表示完整匹配，也可使用 `$1`、`$2` 等捕获组。 |
| `trimStrings` | string[] | 替换前从匹配文本中移除的字符串列表。官方 UI 叫 Trim Out。 |
| `placement` | number[] | 生效来源列表。SillyTavern 源码当前映射：`1` User Input，`2` AI Output，`3` Slash Command，`5` World Info，`6` Reasoning；`0` 是已废弃 MD Display；`4` 是旧 sendAs。 |
| `substituteRegex` | number | 是否在 `findRegex` 中替换宏。源码映射：`0` 不替换，`1` 原样替换宏，`2` 替换并转义为安全 regex 文本。 |
| `minDepth` | number/null | 只作用于聊天历史中不浅于该深度的消息。官方文档说明深度可限制只处理近几条历史。 |
| `maxDepth` | number/null | 只作用于聊天历史中不深于该深度的消息。必须大于 Min Depth 才能生效。 |
| `markdownOnly` | boolean | 只影响显示/Markdown。官方文档把这类限制称为 Ephemerality：可让看到的内容和发给模型的内容不同。 |
| `promptOnly` | boolean | 只影响发往模型的 prompt。 |

## 五、Chat Completion 预设整体结构

SillyTavern Prompt Manager 官方文档说明：Prompt Manager 是 Chat Completion API 的提示词构建系统，控制“发送什么”和“按什么顺序发送”。预设 JSON 保存了采样参数、工具/后端选项、utility prompts、Prompt Manager 的 `prompts` 和 `prompt_order`。

本项目当前重点编辑：

- Overview：`use_sysprompt`、`stream_openai`、`send_if_empty`、新聊天/继续/群聊 nudge 等。
- Sampling：温度、top-p/top-k/top-a/min-p、惩罚、上下文和输出 token、reasoning/web/function calling 等。
- Prompt Graph：`prompts[]`。
- Prompt Order：`prompt_order[]`。
- Extensions：`extensions`。

## 六、预设顶层常见 key

### 1. 上下文与输出长度

官方 Common Settings 文档说明：Response tokens 是 API 最多生成多少 token；Context tokens 是 SillyTavern 会发送给 API 的 prompt 上限，里面包括角色信息、系统提示、聊天历史等。

| key | 类型 | 含义 |
| --- | --- | --- |
| `openai_max_context` | number | Chat Completion 预设的上下文 token 上限。 |
| `openai_max_tokens` | number | 最大回复 token 数。 |
| `max_context_unlocked` | boolean | 是否解除/允许更大上下文范围的 UI 限制。 |
| `stream_openai` | boolean | 是否流式显示回复。官方 Common Settings 提到 Streaming 开启后会逐步显示生成内容。 |

### 2. 采样参数

| key | 类型 | 含义 |
| --- | --- | --- |
| `temperature` | number | 随机性。官方文档说明低温更稳定，高温更发散；`1` 接近原始概率。 |
| `frequency_penalty` | number | 频率惩罚。通常用于降低重复出现过的 token。 |
| `presence_penalty` | number | 存在惩罚。通常鼓励引入新内容。 |
| `repetition_penalty` | number | 重复惩罚。官方 Common Settings 说明 `1` 表示关闭。 |
| `top_p` | number | 核采样。官方文档说明累积概率达到阈值的 token 被保留；`1` 通常表示关闭。 |
| `top_k` | number | 只保留概率最高的 K 个 token；`0` 或后端指定值通常表示关闭。 |
| `top_a` | number | 根据最高 token 概率平方设阈值过滤低概率 token；`0` 表示关闭。 |
| `min_p` | number | 按最高 token 的相对概率剪掉过低概率 token；`0` 表示关闭。 |
| `seed` | number | 随机种子。支持时可提高复现性；`-1` 常表示随机。 |
| `n` | number | 一次请求的候选/生成数量。不同后端支持程度不同。 |

官方 Prompt Manager 文档说明 Utility Prompts 用来帮助 Chat Completion 模型理解发送内容，或在特定交互中指导模型行为。

| --- | --- | --- |

| `new_chat_prompt` | string | 新建单人聊天时使用的 utility prompt。 |
| `new_group_chat_prompt` | string | 新建群聊时使用的 utility prompt。 |
| `new_example_chat_prompt` | string | 示例对话块格式化/新示例聊天相关 utility prompt。 |
| `continue_nudge_prompt` | string | Continue 操作末尾追加的提示。官方文档说明它告诉模型 Continue 时该做什么。 |
| `group_nudge_prompt` | string | 群聊 nudge 模板。官方文档说明它用于强制特定角色回复；留空则禁用。 |

官方 Prompt Manager 文档说明 Format Templates 用来包装来自 World Info 和 Character Cards 的信息。Context Template 文档也说明角色字段可通过 `{{description}}`、`{{scenario}}`、`{{personality}}` 等宏进入模板。

| `names_behavior` | number/string | 角色名处理策略。Prompt Manager 文档说明可调整模型如何识别消息属于哪个角色。 |

### 5. Chat Completion 功能开关

## 七、预设 `prompts[]`

官方 Prompt Manager 文档说明：`prompts` 下的 prompt 是可插入 Prompt Manager 的提示词。`Prompt List` 是拖拽排序界面，越靠上越早发送，越靠下越晚发送；底部通常是 Post-History Instructions。

| key | 类型 | 含义 |
| --- | --- | --- |
| `identifier` | string/number | prompt 唯一标识。`prompt_order[].order[].identifier` 会引用它。默认 prompt 常有固定 ID，例如 `main`、`charDescription`、`scenario`。 |
| `name` | string | Prompt 名称。官方文档说明它不会发送给模型，只用于 Prompt Manager 内部识别。 |
| `enabled` | boolean | 是否启用。禁用后通常不会进入最终 prompt。 |
| `role` | string | 发送该 prompt 的消息角色。官方文档列出 System、AI Assistant、User。JSON 常用 `system`、`assistant`、`user`。 |
| `content` | string | prompt 正文。真正发给模型的内容。可用 SillyTavern 宏。 |
| `system_prompt` | boolean | 是否属于 system prompt 类。源码用它区分 system/user/important prompt 分类。 |
| `marker` | boolean | 标记型 prompt。通常用作占位/锚点，不一定直接等同普通正文 prompt。 |
| `forbid_overrides` | boolean | 禁止被覆盖。源码把 `system_prompt && forbid_overrides` 视作 important prompt；角色覆盖逻辑不应替换它。 |
| `injection_position` | number | 插入方式。源码枚举：`0` = Relative，按拖拽列表相对位置发送；`1` = Absolute / In-Chat，按深度插入聊天历史。 |
| `injection_depth` | number | 当 `injection_position = 1` 时使用。官方文档说明 Depth 0 表示最后一条消息之后，1 表示最后一条消息之前，2 表示倒数第二条之前。 |
| `injection_order` | number | 当多个 absolute/in-chat prompt 落在同一深度时的排序值。源码默认约为 `100`。 |
| `injection_trigger` | string[] | 生成类型触发器。官方文档列出 Normal、Continue、Impersonate、Swipe、Regenerate、Quiet 等；为空表示所有类型都发送。 |
| `position` | string/number | 扩展 prompt 的相对插入锚点。源码中某些 extension prompt 会用它插入 main prompt 前后。 |
| `extension` | boolean | 是否由扩展添加。 |

默认/pinned prompt：

官方 Prompt Manager 文档说明默认 prompt 不能从列表移除，只能关闭。包括 Main Prompt、World Info before/after、Persona Description、Character Description、Character Personality、Scenario、Enhance Definitions、Auxiliary Prompt、Chat Examples、Chat History、Post-History Instructions 等。

## 八、预设 `prompt_order[]`

`prompt_order` 保存“某个角色使用哪些 prompt、以什么顺序、每个是否启用”。Prompt Manager 源码按当前角色 ID 查找对应列表。

| key | 类型 | 含义 |
| --- | --- | --- |
| `character_id` | number/null | 角色 ID。SillyTavern 会按当前角色的 `id` 查找对应 prompt order。`null` 在一些导出或编辑器中可表示全局/默认组，但 SillyTavern 源码主要按角色 ID 匹配。 |
| `order` | object[] | 对该角色生效的 prompt 顺序列表。 |

`order[]` 每项：

| key | 类型 | 含义 |
| --- | --- | --- |
| `identifier` | string/number | 指向 `prompts[]` 中同名 `identifier` 的 prompt。 |
| `enabled` | boolean | 该角色下是否启用这个 prompt。即使 prompt 定义存在，如果这里禁用，也不会作为该角色的启用 prompt 使用。 |

编辑注意：

- 删除或修改 `prompts[].identifier` 会影响所有 `prompt_order[].order[].identifier` 引用。
- 如果新增 prompt，只加到 `prompts` 还不够；通常还要加入目标角色的 `prompt_order` 才会进入 Prompt Manager 列表。
- 顺序越靠后通常越接近最终输出，影响力可能更强，尤其是 Post-History Instructions。

---

## 九、预设 `extensions`

预设的 `extensions` 与角色卡的 `data.extensions` 类似，也是扩展数据容器。

常见 key：

| key | 类型 | 含义 |
| --- | --- | --- |
| `regex_scripts` | object[] | Regex 扩展的 Preset 脚本。Regex 源码显示 Preset 脚本通过 `presetManager.readPresetExtensionField({ path: 'regex_scripts' })` 读取。结构同角色卡 `data.extensions.regex_scripts[]`。 |
| `tavern_helper` | unknown | 酒馆助手等插件可能写入的预设级配置。 |
| `SPreset` | unknown | 第三方预设/插件元数据。 |
| 其他 key | unknown | 任意插件数据。 |

编辑建议：

- `extensions` 必须按“未知字段保留”处理。
- 如果 UI 暂不理解某个 key，不应删除、重排或类型转换。
- 对插件字段做专门编辑前，应先读对应插件源码或文档。

## 十、角色卡与预设的关系

1. 角色卡提供“角色是谁、处境是什么、如何说话、可触发哪些 lore”。
2. 预设提供“如何把角色、用户、世界书、历史、工具和各种提示拼成一次请求”。
3. 官方 Prompts 文档说明，发送给模型的最终 prompt 会组合主指令、角色定义、persona、World Info、历史消息、用户消息、最终指令等。
4. 对 Chat Completion API，Prompt Manager 控制 prompt 的顺序、角色、启用状态、触发类型和 in-chat 注入。
5. 对 Text Completion / Instruct 模型，Context Template / Story String 更直接决定角色字段如何被渲染。

实用判断：

- 修改角色 `description/personality/scenario`：改变角色长期设定，属于每轮都可能影响模型的永久信息。
- 修改角色 `first_mes`：主要影响开局风格和第一轮上下文。
- 修改角色 `mes_example`：影响表达示范，但可能被上下文挤出。
- 修改 `character_book.entries`：适合大量可按关键词触发的世界观/记忆/规则。
- 修改预设 `prompts/prompt_order`：改变最终请求结构和优先级，影响范围通常大于单张角色卡。
- 修改预设采样参数：改变模型输出风格，但不改变角色设定本身。

## 十一、本项目编辑器实现建议

### 1. 必须保留未知字段

角色卡和预设都大量使用 `extensions`，而且不同插件和资源站可能写入自定义 key。编辑器应采用“读懂的字段可视化编辑，读不懂的字段原样保留”的策略。

### 2. UI 中建议优先展示的角色卡字段

- 基础：`data.name`、`description`、`personality`、`scenario`
- 开局与示范：`first_mes`、`alternate_greetings`、`mes_example`
- 高级：`system_prompt`、`post_history_instructions`、`extensions.depth_prompt`
- 元数据：`creator_notes`、`creator`、`character_version`、`tags`
- Lore：`character_book.entries`
- Regex：`extensions.regex_scripts`

### 3. UI 中建议优先展示的预设字段

- 采样：`temperature`、`top_p`、`top_k`、`top_a`、`min_p`、惩罚项、上下文/输出 token
- Utility prompts：`send_if_empty`、`new_chat_prompt`、`continue_nudge_prompt`、`group_nudge_prompt`
- Prompt Manager：`prompts[]` 与 `prompt_order[]`
- 功能开关：`use_sysprompt`、`stream_openai`、`function_calling`、`show_thoughts`、`reasoning_effort`、`verbosity`、`enable_web_search`
- 扩展：`extensions.regex_scripts` 和其他未知扩展 JSON

### 4. 校验规则建议

- 角色卡：
  - `data.name` 不能为空。
  - `alternate_greetings`、`tags` 应为数组。
  - `extensions` 应为对象。
  - `character_book.entries` 应为数组。
  - 条目 `id` 不应重复。
  - Regex 脚本至少需要一个 `placement`，否则不会生效。
- 预设：
  - `prompts[].identifier` 不应重复。
  - `prompt_order[].order[].identifier` 应能在 `prompts[]` 中找到。
  - `openai_max_tokens` 不应超过 `openai_max_context`。
  - `injection_position = 1` 时应有合理的 `injection_depth` 和 `injection_order`。

## 十二、关键参考摘记

- 角色卡是 SillyTavern 的核心概念，是一组设定 LLM 行为的提示集合。
- 角色名、描述、性格、场景是角色永久 tokens；首条消息只在开局发送；示例消息可因上下文不足被挤出。
- Prompt Manager 控制 Chat Completion API 的 prompt 构建策略、发送内容和顺序。
- Prompt 列表中越靠上的 prompt 越早发送，越靠下越晚发送；底部通常是 Post-History Instructions。
- Prompt 的 `Role` 决定作为 System、Assistant 还是 User 消息发送。
- Prompt 的 `Triggers` 决定哪些生成类型会发送该 prompt。
- Prompt 的 In-Chat `Depth` 控制它插入聊天历史的深度。
- World Info 条目按 key 触发并插入 prompt；`content` 是实际插入文本。
- World Info `insertion_order` 越大越靠近上下文末尾，通常影响更强。
- Regex 扩展对匹配文本执行替换；角色 scoped 脚本存在角色卡，preset 脚本存在预设 extensions。
